# 11. Резидентные службы: TTS-воркер и ASR-сервер

## Зачем это всё

Потоки ускоряют синтез на 10–26% (см. docs/09-tts.md), а вот **загрузка модели
в каждом запуске съедает секунды**:

- `say.sh`: **3.4–3.9 с** на загрузку Silero + **0.16 с** собственно синтез;
- `sherpa-onnx-offline`: **~2.0 с** на запуск, счёт — десятые доли секунды.

Резидентные процессы грузят модель ОДИН раз, а дальше отвечают на реплики.

## Замеры на BPI-W3 (проверено на живых службах)

- синтез реплики «Включить ли свет?»:
  - через воркер: **0.21–0.23 с** (RTF 0.17–0.19)
  - холодным путём: **1.9–2.0 с** синтеза + **3.4–3.9 с** загрузка модели
- **полное время отклика `say.sh`: ~0.45 с** через воркер против **~5.5 с** холодного
- ASR через websocket-сервер: **~0.50 с** на фразу против **~2.0 с** холодного,
  распознаёт ровно тот же текст («Включить ли свет в коридоре…?»)
- память: TTS-воркер **~750 МБ**, ASR-сервер **~680 МБ** — примерно **1.2 ГБ**
  на оба, при 8 ГБ на плате свободно остаётся >6 ГБ

Отдельное наблюдение: **первый запрос после старта воркера занимает ~1.9 с**
(прогрев torch-ядер при первом `apply_tts`), дальше стабильно 0.2 с. Если это
не устраивает — прогрев можно сделать прямо при запуске воркера.

## Службы

Обе поставлены как ПОЛЬЗОВАТЕЛЬСКИЕ юниты systemd (не system): работают от
ubuntu, root не нужен, autostart привязан к `default.target` и требует
`loginctl enable-linger ubuntu` (уже включён на плате).

```bash
cp systemd/ttsd.service systemd/asrd.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now ttsd asrd
```

| Юнит   | Что запускает                    | Порт         |
|--------|----------------------------------|--------------|
| `ttsd` | `scripts/ttsd.py` (Silero в памяти) | unix-сокет `~/.assistant/ttsd.sock` (chmod 600) |
| `asrd` | `sherpa-onnx-offline-websocket-server` | TCP **6006, все интерфейсы** |

Управлять:

```bash
systemctl --user status ttsd
systemctl --user restart asrd
journalctl --user -u ttsd -f          # живой лог
```

Статус живого воркера без синтеза: `{"cmd": "ping"}` в сокет — в ответ
придёт `{"ok": true, "threads": 4}`.

## Как работают клиенты

**TTS.** `tts_say.py` сначала пробует воркер; тот не отвечает/падает — скрипт
**молча** делает холодный путь (как раньше). Ломаться от выключенного воркера
никто не обязан, поэтому воркер можно включать и выключать произвольно.
`--no-daemon` заставляет идти холодным путём всегда (удобно для отладки).

Протокол ttsd — unix-сокет, одна строка JSON + `\n`:

    {"voice": "baya", "ssml": "<speak>…</speak>"}      → {"ok": true, "samples": N, "gen_s": 0.15, "threads": 4} + N*4 байт float32
    {"cmd": "ping"}                                    → {"ok": true, "threads": 4}
    {"cmd": "shutdown"}                                → {"ok": true}

Клиент и сервер собирают запрос одной функцией (`core.worker_request`) — договор
в одном месте, а не в двух. Ответ — float32-моно, так как клиенту всё равно
дальше нужна громкость/стерео; разбор — `core.mono_from_bytes` (даёт
перезаписываемый массив, см. comment в коде: frombuffer на bytes read-only).

**ASR.** `scripts/asr_ws.py` читает WAV (моно int16, произвольная частота —
это выход sox-фильтра из listen-and-recognize.sh), и шлёт его протоколу
sherpa-onnx по образцу их python-примера: `rate(4B LE) + len(4B LE) + float32`.
Сервер отвечает строкой; клиент разбирает JSON или возвращает текст как есть.

`listen-and-recognize.sh` при этом **не потерял холодный путь**: если порт 6006
закрыт или сервер не ответил (это видно по коду возврата, не по пустоте вывода),
скрипт пойдёт через `sherpa-onnx-offline`, как и раньше. Пустая реплика —
законный ответ сервера (тишина у микрофона) и холодный путь НЕ запускается.
Какой путь сработал, видно в строке отчёта: «(резидентный ASR-сервер, порт …)»
или «(сервера нет — холодный путь, ~2 с)». Настройки адреса/порта — переменные
`ASR_ADDR` (127.0.0.1) и `ASR_PORT` (6006).

## Грабли, проверенные вручную

- **Кадрирование ответа воркера — режь строку статуса по ПЕРВОМУ `\n`.**
  Сервер пишет статус и payload ПОДРЯД; float32-аудио сплошь содержит байт
  0x0a. Наивное клиентское «читать до `\n`» под нагрузкой получало
  статус+payload ОДНИМ чанком и либо падало на `json.loads`, либо вычитывало
  весь payload в поисках `\n` и получало EOF («воркер закрыл соединение до
  ответа») — при полностью успешном ответе сервера. Симптом на живой плате:
  реплики недетерминированно уходили холодным путём (3–4 из 7), при идеальном
  журнале воркера; в худшем состоянии это тянуло холодный путь (+5 с) и
  работающий синтез воркера выбрасывался. Правильно: `core.read_worker_reply`
  режет по первому `\n`, всё после — начало payload; регрессия —
  `test_worker_framing` (socketpair, склеенный чанк с 0x0a внутри).
- **`pkill -f ttsd.py` убивает сам скрипт-обёртку**: слово «ttsd.py» есть и в
  командной строке того, кто делает pkill (bash -c). Управлять воркером
  надо по PID-файлу (`~/.assistant/ttsd.pid`), который воркер пишет на старте.
- **Обработчик сигналов должен принимать ДВА аргумента** (`signum`, `frame`):
  `def bye(_sig=None)` падает с TypeError при получении SIGTERM (проверено на
  рестарте службы).
- **`--model-type` у websocket-сервера sherpa не такой, как у one-shot**:
  `nemo_transducer` сервер не знает и падает с «'vocab_size' does not exist in
  the metadata». Проще не передавать model-type вовсе: двойная загрузка
  модели при старте резидентного процесса не страшна.
- **ASR-сервер слушает 0.0.0.0:6006** — флага привязки адреса у него нет.
  Порт открыт на LAN (192.168.0.171:6006). Сервер только ДЕКОДИРУЕТ звук и не
  даёт управления, так что риск минимален, но при желании закрывается
  правлением фаервола на плате/роутере.
- `/usr/bin/time` на Ubuntu-плате **ОТСУТСТВУЕТ** — мерить через bash `time`
  или python (subprocess + time.time()).

## Отладка

- Воркер не отвечает → `systemctl --user status ttsd` и `~/.assistant/ttsd.log`.
- Проверить, что воркер вообще жив: ping через сокет (см. выше).
- «Клиент ушёл холодным путём» — это видно в строке отчёта say.sh:
  `воркер | потоков 4` или `модель 3.41s | потоков 4`.
